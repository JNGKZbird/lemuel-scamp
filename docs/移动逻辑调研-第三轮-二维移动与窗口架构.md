## 0. 摘要（先看这页）

1. **「全屏二维移动」不是一个问题，而是三个可以独立拍板的问题**：窗口怎么承载（小窗/覆盖层）、空间上怎么走（地面线/自由 2D/重力平台/2.5D）、纵向用什么视觉表现（走/漂浮/攀爬/跳跃/滑行）。委托书把它们合成了一个「2D 控制器」，但错误组合会导致「技术做对、看起来错」。
2. **第一轮的核心视觉结论在本轮联网复核中再次成立**：纯侧视美术下，水平位移用侧视走路最自然；纵向位移如果继续用同一套 Move 动画，滑步是结构性的，调参救不了。成熟 2D 桌宠要么只在地面线活动，要么用攀爬/下落/跳跃/飞行专用动作，没有找到「侧视走路自由上下」的成功案例。
3. **成熟桌宠的主流空间模型不是自由 2D，而是「地面线＋重力/平台」**：Shimeji 系走地板、爬墙/天花板、会掉落；Ark-Pets 有平面重力、自由落体、站在窗口边缘、宠物互斥；AI-Desktop-Pet 把地板、窗口顶边做成平台，明确表示「不做弹道跳跃」。这些都需要专用动画或姿态。
4. **窗口架构上，小窗和覆盖层各有明确适用面**：小窗合成面积小、改动面小，适合当前两只宠物；每屏透明覆盖层适合多宠、窗口平台、全屏演出，但 DWM 会整窗透明合成，且点击穿透/多屏 DPI 复杂度显著上升。AI-Desktop-Pet、Degu、mini-tanjiro 都采用了覆盖层；VPet、BongoCat 等采用小窗。
5. **Tauri v2 技术事实（源码/文档级）**：`Monitor.workArea` 可用，单位是**物理像素**；`window.screen` 是 CSS 像素且在多屏/WebView2 下不可靠；`setPosition` 接受逻辑或物理位置，但跨混合 DPI 屏必须统一口径；点击穿透是**整窗开关**，Tauri 不做透明像素级命中；Tao 0.37.1 的 `set_ignore_cursor_events` 会连带切换 `WS_EX_LAYERED`，第三方 Tauri 桌宠实测这会引发透明 WebView2 的合成异常，当前项目需要复测。
6. **给本项目的推荐组合**：本阶段**保留两只小窗**，移动核心做成纯 TS、窗口无关；空间模型先做「**分层生活面＋两段式移动**」——同层横向用 Move 走路，换层用「天使漂浮/滑翔」过渡，而不是斜向直走；不新增骨骼动画，但先做 2–3 种纵向视觉原型让你肉眼选。若漂浮被否，退到「地面线＋拖拽改 y」，核心不变。长期若做窗口平台/多宠/捣乱，再迁移到「每屏一个透明覆盖层」。
7. **当前代码里可以立刻确认的三个优化/风险点**：`window.screen.width/height` 被当作活动范围与角色尺寸基准；`setPosition`/`set_hit_boxes` 每帧无条件 IPC；Tao 穿透开关会切换层样式。它们都比「写 2D 控制器」更早影响移动的手感和稳定性。

## 2. 先把问题拆成三轴

| 轴 | 选项 | 决定什么 | 主要代价 |
|---|---|---|---|
| **A. 窗口架构** | 小窗跟随 / 单个全屏覆盖层 / 每屏覆盖层 / 混合 | 渲染成本、点击穿透、多屏/DPI、多宠扩展 | 覆盖层要重构命中与坐标；小窗跨屏要处理 DPI |
| **B. 空间模型** | 地面线 / 自由 2D / 重力平台 / 2.5D 深度 / 路径点 | 能去哪、怎么选目标、边界与碰撞 | 自由 2D 与现有动画冲突；重力平台要新动画/窗口枚举 |
| **C. 纵向视觉** | 侧视走 / 漂浮 / 攀爬 / 跳跃/下落 / 深度缩放 / 接受滑行 | 看起来是否自然 | 除「接受滑行」外都需要新表现或新资产 |

**推荐决策顺序：先 C（视觉能不能接受）→ 再 B（空间语义）→ 最后 A（窗口承载）。** 这跟委托书「先写 2D 控制器」的顺序相反，但能避免做完才发现看起来不能接受。

## 3. 现状复核（以最新源码为准）

### 3.1 窗口与循环

- `angel2`：`src-tauri/tauri.conf.json` 中 260×280、透明、无边框、`alwaysOnTop`、`skipTaskbar`、不可缩放。
- `angel`：由 `App.tsx` 在 `angel2` 基础上拉起，初始在主窗左侧 290 logical px；两个窗口各自跑自己的 `requestAnimationFrame` 循环，互不隶属、没有共享移动状态或碰撞。
- `console`：总控台单独窗口；移动任务不碰。

### 3.2 移动现状

- 状态机：`idle / walk / turn / poke / sit / sleep`；`x` 自主变化，`y` 只在拖拽时变化。
- `pickNext()` 只在 x 轴随机距离，`contentClamp()` 用渲染器的可见内容包围盒夹左右；**y 没有自动夹取**。
- 走速 `walkSpeed = MODEL.stance × (displayH / modelH)`；`displayH = min(window.screen.height × 0.163, 252)`。
- 活动范围写死为 `window.screen.width`（注释「活动范围＝设备整块屏幕」）；没有使用 Tauri monitor/workArea。
- 转身 0.15s 线性；`yaw` 在着色器里是对顶点 x 做 `cos(yaw)` 压缩，只有 0/π 两个朝向，不是真正的 3D 旋转。
- 拖拽用 `PointerEvent.screenX/screenY`，以窗口 logical x/y 为基准；移动超过 4px 才算拖拽；短按触发 `Interact`。

### 3.3 IPC 与穿透

- `pushMove()` 每帧调用 `setPosition(LogicalPosition(round x, round y))`，用 `pending` 避免并发；即使位置没变也会调用。
- 每帧把可见内容包围盒、关闭钮、菜单推给 Rust `set_hit_boxes`；拖拽时整块 canvas 纳入。
- Rust 端每 8ms 轮询一次光标，用 `outerPosition()`（物理）＋局部 CSS 框×`scaleFactor` 判断是否在命中框内，状态变化时调用 `set_ignore_cursor_events`。
- 初始全穿透，等前端推命中框后再放开。

### 3.4 技术版本

- `@tauri-apps/api` 2.12.4、`@tauri-apps/cli` 2.12.3。
- Rust：`tauri` 2.12.4、`tao` 0.37.1、`tauri-runtime-wry` 2.12.2、`wry` 0.57.0。
- 因此 `Monitor.workArea`、`availableMonitors/currentMonitor/monitorFromPoint` 都可用；2025 年的跨屏 DPI 历史 bug 修复也应在当前版本中（见 6.2），但仍要实测。

### 3.5 与委托书的口径差异

- 委托书说「移动范围＝设备整块屏幕、没有多屏/DPI 处理」——源码确认。
- 委托书说「y 没有自动夹取」——源码确认。
- 委托书将 `walkMin/walkMax` 称为占位值——源码注释确认。
- 委托书建议「新建 `src/pet/movement.ts`、纯逻辑、Behavior 注入」——与现有架构兼容，本轮报告沿用。
- 需要修正的假设：**不要假设 `window.screen` 与 Tauri monitor 是同一口径**；两者的单位/当前屏语义不同，详见第 6 节。

**归纳：**

1. 成熟 2D 桌宠没有把「侧视走路上/下」当默认能力；纵向要么是专用动作（攀爬/下落/跳跃），要么是飞行（Angelina-pet），要么根本不做自主纵向。
2. 窗口架构的两种主流：小窗（VPet、BongoCat 等）和每屏覆盖层（Degu、mini-tanjiro、Shimeji 系）。单覆盖层承载多宠也常见（AI-Desktop-Pet）。
3. 「点击穿透＋命中区」不是附属功能，而是桌宠运行时的一等公民；覆盖层越大，命中/穿透的工程成本越高。
4. 行为调度普遍是加权随机＋条件＋冷却；不需要行为树，但需要「锁/预约/个人空间」这类防打架机制。

## 5. 空间模型对比

| 模型 | 视觉自然度（现有素材） | 2D 自由感 | 前置/成本 | 结论 |
|---|---|---|---|---|
| **地面线** | 高（Move 本来就是横向走路） | 低（y 固定或拖拽） | 无新动画；低 | 保守、稳 |
| **自由 2D 直走** | 低（上下滑步） | 高 | 无新动画；中 | **不推荐** |
| **分层生活面＋两段式** | 中–高（同层走、换层漂浮） | 高（可达全屏） | 无新动画；中 | **本轮推荐做原型** |
| **重力/平台（Shimeji）** | 高（有攀爬/下落） | 中–高（受平台限制） | 新动画＋窗口枚举；高 | 长期 |
| **路径点/锚点** | 取决于动作 | 中（离散点） | 可能需新动作；中 | 未来 |
| **2.5D 深度（y＝远近）** | 中（靠缩放/阴影建立深度） | 高 | 程序化缩放；中 | 可做视觉原型 |
| **接受滑行** | 低 | 高 | 无；低 | 不推荐 |

### 5.1 为什么「自由 2D 直走」不推荐

- 第一轮调研已经指出：侧视走路的脚部接触方向是水平的，纵向位移没有对应的地面支撑；把同一套 Move 拿去走上下，必然滑步。
- 本轮补充证据：
  - 2D 游戏里上下楼梯/斜向移动的常见做法是**专用上下动画＋按步幅移动**；否则会出现「滑冰」。`[C]`
  - 侧视角的「平面纵深」需要扁平的决策圆/地平线、透视缩短或深度缩放；不是简单把 y 当 x 走。`[C]`
  - Shimeji 用攀爬/天花板动作；Ark-Pets 用重力/下落；Angelina-pet 用飞行；没有找到「侧视走路连续上下」的成功样本。`[B]`
- 我们这个角色的着色器 `yaw` 只是水平压缩，没有真正的上下/斜向姿态；Move/Relax/Sit/Sleep/Interact 里也没有 climb/fall/jump/flight。

### 5.2 推荐：分层生活面＋两段式移动

把工作区（work area）横向分成 2–3 条「生活带」（lane），默认 3 条：

- **同层移动**：继续用 Move，横向走；目标 x 在同层，自然。
- **换层移动**：先走到当前层的换层点（或原地），进入「漂浮/滑翔」状态，纵向移动到目标层的目标 y，再横向走到目标 x；不是斜向直走。
- **漂浮表现**：优先用 Relax 姿态（站立/呼吸）＋缓入缓出的纵向速度＋轻微正弦上下浮动/缩放，表现「天使悬浮」；也可以用 Move 做低速滑翔，但需要视觉对比后定。`[C]`（设计假设，需原型验证）
- **目标选择**：随机目标先选 lane，再选 x；同层概率高，换层概率低；换层有冷却，避免频繁上下。
- **边界**：只在 work area 内；顶部留出安全边距，不让角色贴到屏幕顶（漂在天花板下会像 bug）。
- **优点**：可达全屏任意点，满足「二维目标」；没有连续上下滑步；不需要新骨骼动画；与现有状态机兼容。
- **风险**：漂浮是否好看、是否符合角色设定，必须你肉眼拍板；如果不接受，退到地面线。

### 5.3 2.5D 深度（备选视觉）

- 把屏幕 y 解释为「远近」：越往上越远，角色略微缩小；越往下越近，略微放大；可配一个柔和的地面阴影/光晕。`[C]`
- 这能让纵向移动读成「走向/走离镜头」，而不是滑步；但侧视角色＋缩放的组合需要试。
- 不建议首版就做；可以作为漂浮方案的对照原型。

### 5.4 重力/平台（长期）

- 地板＝work area 底部（或任务栏上方）；平台＝可见窗口顶边、任务栏、自定义锚点。
- 需要：窗口枚举（Win32 `EnumWindows` + DWM 过滤）、平台矩形、重力/阻尼、下落/着陆、攀爬/跳跃动画。
- Shimeji/AI-Desktop-Pet 证明这套可行，但工作量远大于本轮；而且会把「移动」升级成「场景交互」，应等捣乱/寻路立项后再做。`[B]`

## 6. 窗口架构对比

| 架构 | 合成成本 | 多屏/DPI | 穿透与多宠 | 改动面/适用 |
|---|---|---|---|---|
| **小窗跟随（现状）** | 低（只合成小面积） | 需自己处理跨屏 DPI；当前用 window.screen 不可靠 | 整窗开关；每宠一窗、独立 | 最小；当前 2 只 |
| **单个全屏覆盖层** | 高（DWM 整窗透明合成） | Windows 混合 DPI 下整窗只有一个 DPR，易错 | 命中区/穿透复杂；多宠一网打尽 | 大；多宠/全屏演出 |
| **每屏覆盖层** | 中–高（每屏整窗合成） | 每屏独立 DPR/高度，最稳 | 每屏命中；需跨窗共享模拟 | 很大；多屏/多宠 |
| **混合（小窗＋纯核心）** | 低 | 可渐进 | 沿用现状 | 中；**本轮推荐** |

### 6.1 为什么本阶段不切覆盖层

- 目前只有两只宠物，小窗合成面积小、资源低；切覆盖层会同时重写窗口创建、命中、坐标、拖拽、菜单、关闭、双窗协同，远超「移动」范围。
- 覆盖层的优势主要在多宠、窗口平台、全屏演出；这些是后续「捣蛋/寻路」的事，不是本轮。
- 纯移动核心如果做得好，未来切覆盖层只需要换适配层，不必重写运动逻辑。

### 6.2 覆盖层的真实成本（如果未来要做）

- **DWM 整窗 alpha 合成**：一个 Live2D 桌宠项目的性能整改记录指出，全屏透明置顶窗口＋全屏 canvas 会让 DWM 对每个损伤帧做整窗 alpha 合成；空闲态如果不按需重绘，会持续占 GPU。`[B]`
- **命中/穿透竞态**：同一记录提到，光标进入交互区到 `setIgnoreMouseEvents(false)` 生效最多约 33ms＋切换延迟，快速点击可能穿过；需要指针捕获/物理键状态兜底。`[B]`
- **混合 DPI**：单个跨虚拟桌面的窗口在 Windows 上只有一个 DPR；显示器缩放不同时，另一侧可能画错/错位。每屏一个覆盖层是更稳的方案。`[B]`
- **多屏覆盖层实现**：Degu 在 2026-06-29 的 v0.1.14 明确把多屏渲染拆成「每屏一个透明覆盖层」，以适配不同高度/DPI；mini-tanjiro 也是每屏一层。`[B]`
- **坐标统一**：AI-Desktop-Pet 的做法是「所有跨 IPC 坐标用物理像素，覆盖层入口处除以 scale 一次转成 CSS 逻辑像素」；这比在每层混用逻辑/物理更稳。`[B]`

## 7. Tauri v2 事实与坑（本轮重点）

### 7.1 Monitor API 与单位

- `availableMonitors()` / `currentMonitor()` / `primaryMonitor()` / `monitorFromPoint(x,y)` 返回 `Monitor`：`name`、`position`（PhysicalPosition）、`size`（PhysicalSize）、`scaleFactor`、`workArea`（`{position, size}`）。
- **`position`、`size`、`workArea` 全部是物理像素**；窗口创建选项 `x/y/width/height` 和 `setPosition` 则接受逻辑或物理（用 `LogicalPosition`/`PhysicalPosition` 明确指定）。`[A]`
- Windows 端 `workArea` 的实现就是 `GetMonitorInfoW` 的 `rcWork`（排除任务栏/Dock）；源码在 `tauri-runtime-wry/src/monitor/windows.rs`。`[A]`
- `cursorPosition()` 是**物理像素**，相对桌面左上角；多屏/负坐标时可为负。`[A]`
- `window.screen.width/height` 是 **CSS 像素**，而且不保证代表「当前窗口所在显示器」：WebView2 在多屏/PerMonitorV2 下有屏幕指标不一致的报告；MDN 也说明浏览器通常取窗口中心所在屏，但实现并不统一。`[A/B]`
- 当前代码用 `window.screen.width` 当活动范围、`window.screen.height × 0.163` 当角色显示高度；如果窗口移到副屏或不同缩放屏，**活动范围/角色尺寸可能按错屏计算**。这不是「大概不准」，是需要在真机逐屏核对的坐标系问题。

### 7.2 多屏与混合 DPI

- Tauri 有过一个真实的 Windows 混合 DPI bug（#12626）：窗口在 250% 与 100% 屏之间移动时逻辑尺寸被反复放大，最终可能出现 12668×9840 这种不可用尺寸；该 issue 在 2025-02-27 由 `tao#1056` 修复。当前项目用 tao 0.37.1，理论上已包含修复，但仍需实测跨屏拖动/自动移动。`[A/B]`
- 混合 DPI 的「空隙」常常是 DPI 虚拟化造成的逻辑坐标假象，不是物理空隙；PerMonitorV2 进程能看到物理矩形，但 Windows 的鼠标跨屏边界仍可能有逻辑死区。`[B]`
- 一个 Qt 桌宠的现场记录很典型：v4.2.1 把所有移动路径都钳制到「窗口当前所在屏」，导致窗口出不了当前屏→中心进不了另一屏→永远换不了屏，形成自锁；同时主副屏 100%/125% 造成 216px 的逻辑死区，角色贴边探头也够不到副屏。这个案例说明：**「先夹到当前屏」和「允许跨屏」必须二选一，不能既夹又期望跨。** `[B]`
- 网上的窗口状态恢复实践也提醒：持久化的物理位置/尺寸在 DPI 变化后可能落在错误屏/错误大小；恢复前要用当前 monitor 列表校验，并在 `ScaleFactorChanged` 后重新夹取。`[B]`

**对本项目的建议（待实测后定）：**

1. 内部统一用**物理像素**做 monitor/window 几何，只有在调用 `setPosition` 时按目标窗口当前 scale 转成逻辑，或在入口处统一转换一次；不要在多个层混用。
2. 先做「**每只宠物绑定一块显示器**」：在自己的 work area 内活动，不跨屏；把跨屏留到后续。这样能绕开混合 DPI 的大部分坑。
3. 如果一定要跨屏，先做「**跨屏专用策略**」：不夹当前屏；在边界检测目标屏的 work area；跨屏时按目标屏 scale 重算窗口位置；在 `onScaleChanged` 后重新夹取；并验证任务栏高度不同的情况。
4. 每 1–2 秒比较一次 monitor 布局快照（插拔/分辨率/DPI/任务栏移动），变化时重算边界，而不是只在启动时取一次。AI-Desktop-Pet 的 Rust 轮询就是这么做的。`[B]`

### 7.3 点击穿透：Tauri 只提供整窗开关

- Tauri 官方明确不做「透明像素自动穿透」；维护者在 issue #13070 里说不会实现，建议按需切换 `set_ignore_cursor_events`；跟踪 issue 是 #6164。`[A]`
- `set_ignore_cursor_events` 是**窗口级**，不是 WebView 级（issue #10564）；一个窗口内多个 WebView 不能分别穿透。`[A]`
- 当前项目的方向是对的：前端推窗口局部命中框 → Rust 每 8ms 读全局光标/窗口物理位置 → 只在状态变化时切换。这个模式比前端 `mousemove` 轮询稳，因为窗口忽略鼠标后 DOM 收不到事件。`[A/B]`
- **Tao 0.37.1 的实现细节**（源码确认）：`IGNORE_CURSOR_EVENT` 这个标志在生成扩展样式时同时加上 `WS_EX_TRANSPARENT | WS_EX_LAYERED`；关闭时两者一起移除。也就是说，每次从「穿透」切到「可交互」都会移除 `WS_EX_LAYERED`。`[A]`
- 第三方 Tauri 桌宠（AI-Desktop-Pet）在 `overlay.rs` 里明确记录：Tao 的 `set_ignore_cursor_events(false)` 会剥离 `WS_EX_LAYERED`，在活的透明 WebView2 表面上切换层样式会导致合成异常（整屏发白/磨砂）；他们的对策是**永久保留 `WS_EX_LAYERED`，只翻转 `WS_EX_TRANSPARENT`**，并每 tick 读取真实样式位，防止被 Tao 的其他调用覆盖。`[B]`
- 当前项目的小窗是否也会出现这个异常，需要复测：把鼠标反复移入/移出角色，观察是否有白闪/磨砂/透明丢失。如果有，建议在 Rust 侧做同样的「只翻 `WS_EX_TRANSPARENT`、保留 `WS_EX_LAYERED`」的封装，而不是直接调 Tao API。
- WebView2 运行时本身在 144/145 版本出现过透明回归（灰底/不透明）；这是环境层风险，排查透明异常时要记录 WebView2 版本。`[B]`

### 7.4 拖拽坐标

- `PointerEvent.screenX/screenY` 是**CSS 像素**（不是物理像素）；触摸可能是小数；在 125% 缩放下与窗口几何通常差 1px 左右，属于可接受误差。`[A/C]`
- 浏览器对 `screenY` 的语义有「视口顶」和「外框顶」两种实现；页面缩放会破坏窗口几何假设（本项目没有页面缩放，风险较低）。`[C]`
- 当前拖拽用 `e.screenX - x`（x 是 Tauri logical 坐标）。单屏、同一缩放时两者口径基本一致；**跨混合 DPI 屏时可能跳变**，这是必须实测的点。
- 更稳的候选：
  1. 用 Tauri `cursorPosition()`（物理）＋ `outerPosition()`（物理）＋ `scaleFactor()` 算 delta，整套物理口径；
  2. 用 `clientX/clientY`（窗口局部 CSS）＋窗口 logical 位置，避开全局屏幕坐标；
  3. 在拖拽开始时记录锚点，跨屏 `onScaleChanged` 时重设锚点。
- 不建议用 `startDragging()`（OS 原生拖拽）做带动画的拖拽：第三方记录指出它在 Windows 上可能占用 UI 线程、冻结 CSS 动画；自定义拖拽更适合。`[C]`

### 7.5 性能与 IPC

- 每帧 `setPosition`：Tauri 的 `setPosition` 是 IPC 到原生窗口操作，不是 CSS transform；一个桌宠开发记录显示，按鼠标事件（60+ 次/秒）直接调用会卡，改成 `requestAnimationFrame` 内每帧一次后顺畅。当前代码已经用 rAF＋`pending`，方向正确。`[C]`
- 但当前 `pushMove()` **即使位置没变也调用**；idle 时也在每秒 60 次 `setPosition`。建议改成「取整后的位置与上次不同才推」。
- 每帧 `set_hit_boxes` 的角色包围盒会随动画变化，但**窗口平移本身不需要重推**：Rust 每次用当前 `outerPosition + 局部框` 计算屏幕命中区。可以改成「内容包围盒变化超过阈值（例如 1px）才推」，把两窗 120 次/秒的 IPC 降下来。
- Rust 命中轮询 8ms（125Hz）比 AI-Desktop-Pet 的 16ms 更密；当前命中框小，问题不大，但可以测 CPU。命中框越多/窗口越大，越要控制。
- 全屏覆盖层的成本见 6.2；小窗方案在「两只宠物」规模下更稳。
- 任务栏自动隐藏：`rcWork` 可能等于整块显示器；如果宠物要「站在任务栏上方」，不能只信 workArea，还要判断任务栏当前可见性/位置。项目 `lib.rs` 的 `console_set_maximized` 里已有 `SHAppBarMessage(ABM_GETSTATE/ABM_GETTASKBARPOS)` 的处理，未来可抽成只读的几何 helper（不要改动总控台行为）。`[A/B]`
- 全屏应用出现时是否自动隐藏宠物：本轮不做；未来可用「覆盖整块显示器且无 `WS_CAPTION`」的判定（dsh-pet PR #18 的做法），避免把普通最大化窗口误判成全屏。`[B]`

## 8. 视觉：侧视角色怎么不滑步

### 8.1 结论

- 水平：Move 动画＋横向位移，速度匹配，最自然。
- 纵向：现有素材下有三条路：
  1. **漂浮/滑翔**（用 Relax 或低速 Move，缓入缓出＋轻微上下浮动），把「上下」解释成飞行，而不是走路；Angelina-pet 的自由形态是这条路的先例。`[B]`
  2. **2.5D 深度缩放**，把 y 解释成远近，靠缩放/阴影建立深度。`[C]`
  3. **专用攀爬/下落/跳跃**，最自然，但需要新动画/新资产，超出「只做移动」范围。
- 不建议：继续用 Move 走上下，接受滑行。用户对视觉比例/细节敏感，这条路大概率过不了肉眼验收。

### 8.2 漂浮方案的具体建议（待原型）

- 进入条件：目标层与当前层不同；优先从 idle 进入，walk 中途则先走完/淡出到 idle，再漂浮，避免脚部动作和位移语义打架。
- 姿态：Relax（站立呼吸）比 Move（走路）更像悬浮；如果 Relax 的腿脚太「站」，可以试 Move 低速＋轻微缩放；两种都做 5 秒对比。
- 速度：纵向慢于横向（例如横向走速的 0.5–0.7），缓入缓出；不要匀速直线，像电梯。
- 浮动：位移上叠加 1–2px 的正弦 bob，频率低；不要每帧抖动。
- 朝向：保持左右 facing；漂浮时不需要「上下朝向」。
- 结束：到目标层后回到 idle 或直接接 Move 走剩余 x；不要在半空直接切走。
- 频率：换层是低频事件，不是每次散步都上下；否则会像电梯。

### 8.3 2.5D 深度方案的具体建议（对照原型）

- y 映射到 depth：顶部略小（例如 0.92），底部略大（例如 1.04）；幅度要小，别让角色尺寸跳。
- 可加一个非常淡的地面阴影/光晕来锚定「地面」；不要加复杂粒子。
- 目标选择偏向「同深度带」，换深度时走斜向？——斜向仍会滑，建议同样用两段式/漂浮过渡。
- 需要你肉眼判断「这是走远/走近，还是只是变小了」。

### 8.4 视觉验证纪律

- 做 2–3 个对照原型（漂浮 / 深度 / 原始滑行），录 5–10 秒同场景视频/截图，在 100%/125%/150% 下各看一次。
- 用户对 9% 比例失真都敏感，不能只用「看起来正常」；要记录缩放比例、y 范围、角色显示高度。
- 视觉决策留档（截图＋选择理由），放 `docs/` 或视觉决策档案。

## 9. 多宠协同与未来接口

- 现状：两窗独立，可能重叠/穿模；没有共享移动状态。
- 可选策略：
  - **完全独立**（最简单；重叠时看起来像穿模）。
  - **简单避让/分离**（检测另一只的包围盒，保持最小间距；不改变各自行为）。
  - **目标预约/联合行为**（AI-Desktop-Pet 的 BehaviorDirector：锁、联合预约、个人空间；本轮不做）。
- 本轮建议：先独立；如果实测重叠频繁，再加「软分离」——只推移目标点/当前位置，不引入全局调度器。`[B/C]`
- 未来接口：
  - `moveTo(x, y)`、`randomTarget()`、`pause/resume()`、`setBounds()`、`onArrive()`。
  - `PlatformProvider`（未来窗口平台）与 `Perception`（光标/窗口）分开；本轮只留 `moveTo`，不实现窗口感知。
  - LLM/Agent 只出意图（去哪/做什么），由本地移动层验证执行；不要让 LLM 直接改坐标或动画名。这与第二轮调研的结论一致。

## 10. 可测架构与测试计划

### 10.1 模块边界

新增 `src/pet/movement.ts`（名称可调），只依赖纯类型：

```ts
type Vec2 = { x: number; y: number };
type Bounds = { left: number; top: number; right: number; bottom: number };
type MoveTarget = { x: number; y: number; kind: "walk" | "float" | "auto" };
type MoveState = {
  pos: Vec2; target: MoveTarget | null; facing: 1 | -1;
  mode: "idle" | "walk" | "turn" | "float" | "arrive";
  timer: number; seed: number;
};
step(state, dt, bounds, options): MoveState;
```

- 不 import React/Tauri/DOM/settings；`Behavior` 与屏幕几何都由外部注入。
- RNG 注入（mulberry32/seed），保证测试可复现；不要用全局 `Math.random` 在核心内。
- 固定步长：建议 60Hz 累加器（`fixedDt = 1/60`），渲染插值可选；避免不同帧率下速度/转身不一致。`[C]`
- 速度、转身、到达阈值、换层概率、漂浮速度都放参数表，不写死在状态机分支。

### 10.2 适配层（App.tsx）

- 只负责：读当前 Behavior、读 bounds（monitor/workArea）、把 `MoveState.pos` 映射到 `setPosition`、把 `mode/facing` 映射到动画、把可见框推给 Rust。
- 移动数学全在 `movement.ts`；App.tsx 不再自己算 `x += dirX * speed * dt`。
- 只有位置取整后变化才 `setPosition`；只有包围盒变化超过阈值才 `set_hit_boxes`。

### 10.3 测试清单（`tools/test-movement.ts`）

- 边界：work area 四边、负坐标、多屏矩形、任务栏高度；角色包围盒贴边。
- 目标：到达、接近减速、同层/换层、目标在边界外。
- 转身：0.15s、打断、从 walk 到 float 的合法转移。
- 拖拽接管/释放：暂停自主行为、松手恢复、y 不越界。
- 浮点稳定：大 dt 上限、0 dt、NaN/Infinity 防护、固定步长一致性。
- 多宠：最小间距、两个目标重合时的确定性处理。
- 确定性：同一 seed 同一输入序列 → 同一轨迹。
- 坐标系：physical↔logical 转换、monitor workArea 转换、scale 变化。

### 10.4 真机验收（下一阶段）

- 单屏 100%/125%/150%；双屏不同缩放；负坐标副屏；任务栏自动隐藏。
- 左右/上下/换层/跨屏（若允许）/拖拽/点击穿透/菜单/关闭。
- 两窗同时活动；idle CPU/GPU；`setPosition` 频率；白闪/磨砂；掉帧。
- 这些数据本轮没有采集；不要在报告中伪造。

## 11. 完整方案组合与推荐

### 11.1 四个组合

| 组合 | 窗口/空间 | 纵向视觉 | 满足二维/成本 | 风险/结论 |
|---|---|---|---|---|
| **甲 保守地面线** | 小窗；地面线，y 仅拖拽 | Move 横向 | 部分（任意 x，y 不可自主）；低 | 可能不满足产品预期 |
| **乙 分层生活面（推荐原型）** | 小窗；2–3 层，同层走、换层漂浮 | Relax/低速 Move＋浮动 | 是（任意 x/y 目标，两段式）；中 | 漂浮视觉需拍板 |
| **丙 长期 Shimeji 覆盖层** | 每屏覆盖层；地板＋窗口平台＋重力/攀爬 | 攀爬/下落/跳跃 | 是；高 | 需新动画、窗口枚举、重构 |
| **丁 小窗自由 2D 直走** | 小窗；连续 x/y | Move 直接上下 | 是；中 | 滑步；不推荐 |

### 11.2 推荐

**本轮：乙（分层生活面＋两段式）＋小窗＋纯移动核心。**

- 先做视觉原型：漂浮 / 2.5D 深度 / 原始滑行对照，5–10 秒，真机看；你选一个再写正式控制器。
- 若漂浮被否：退到甲（地面线＋拖拽 y），移动核心不变，只换策略。
- 不建议直接做丁；不建议本轮切丙。
- 若未来要做「窗口平台/捣乱/多宠」，丙是正确方向；届时把 `movement.ts` 的适配层换成覆盖层即可，核心可复用。AI-Desktop-Pet 已经证明 Tauri 覆盖层＋纯 TS PetEngine＋Rust 命中/光标轮询这条路可行。`[B]`

### 11.3 分阶段

1. **阶段 0（不动代码）**：完成本报告的拍板；补真机测量（monitor/DPI/拖拽/性能/穿透）。
2. **阶段 1（视觉原型）**：浏览器或独立沙盒里做 3 种纵向表现；你选。
3. **阶段 2（纯核心）**：`movement.ts` ＋ `test-movement.ts`；不接窗口。
