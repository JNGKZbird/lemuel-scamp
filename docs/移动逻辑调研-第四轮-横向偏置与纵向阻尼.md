## 0. 摘要（先看这页）

1. **两条规则不是临时补丁，它们正好对应 2.5D 横版清关（belt-scroll）的成熟做法**：x 是横向，y 是纵深；纵向速度常被打折（示例 0.6 倍），角色被限制在一条“地板带”里；只用左右朝向的精灵就能上下走。`[B]`
2. **最小可实现模型**：目标斜率用**三角分布**（越陡概率越小，最大斜率 k），执行时用**斜率锥** `|vy| ≤ k|vx|`。两者共用同一个 k，规则 1 管“想不想走陡”，规则 2 管“实际能走多陡”。
3. 斜率锥有一个很好的性质：`|vy|` 的上限 = `k·|vx| = k·s·cosθ`，随 θ 增大单调减小，θ=90° 时为 0。**规则 2 因此是精确满足的，不是近似。**
4. 等距/2.5D 游戏也常把纵向速度设为横向的 0.5；但那是投影造成的“看起来一样快”，与我们的“故意让纵向变慢”是同一类工程手段，不是同一条公式。`[C]`
5. **侧视精灵不需要上下行走动画**：横版清关的常见做法是只保留左右朝向，上下移动复用左/右走路帧，记住最后的左右朝向即可。我们的 Spine 正好可以这样做。`[B]`
6. 大鹅（Desktop Goose Linux 移植版）是另一条证据：它用 `ISO_SCALE {1.3, 0.4}` 的程序化 2.5D 骨架自由 2D 移动，每段目标还带随机抛物线曲率；它不是侧视贴图滑步，但“2.5D 平面＋纵向压缩”的思路可以借。`[B]`
7. **推荐方案 A**：小窗保留；`k=1/3`（约 18.4°）；目标斜率三角分布；执行 `|vy| ≤ k|vx|`；太陡的目标先走横向路点；可选低幅曲率；不新增动画；滑步接受。
8. **本轮不做**：不改 App.tsx 移动循环、不写正式控制器、不启动 GUI、不跑 tsc/测试；先出模型与测试口径，等你拍板。

## 2. 两条硬下限的正式定义

### 2.1 规则一：方向概率递减

设目标方向相对水平线的夹角为 θ（0 ≤ θ ≤ 90°）。要求目标方向密度 `p(θ)` 随 θ 非增；纯竖直方向 `p(90°)=0`，或至少概率低到可以忽略。工程上用两种方式实现：

- **硬上限**：把目标斜率限制在 `|dy/dx| ≤ k`，在 `[-k, k]` 上取三角分布（峰值在 0，边界为 0）。这同时满足“越陡越少”和“纯竖直为 0”。
- **软分布**：在 `[0, θmax]` 上取 `p(θ) ∝ cos^n θ`，或用 von Mises 分布（均值 0，集中度 κ）截断；纯竖直仍为 0 或极小。

**v1 推荐三角斜率分布**：采样简单、边界明确、可精确测试。

### 2.2 规则二：竖直速度递减

设标称速度 s，目标方向 θ。要求竖直速度满足：

```
|vy| ≤ k · |vx|
vx = s · cosθ · sign(dx)
vy = s · sinθ · sign(dy)   // 目标速度，随后被上式夹取
```

因此 `|vy|` 的上限是 `k·s·cosθ`：

- θ=0°：上限 k·s，但目标 vy=0，实际竖直速度为 0；
- θ 增大：上限按 cosθ 单调减小；
- θ=90°：上限 0，纯竖直无法移动。

这就是规则 2 的精确实现。它不要求“竖直速度从 0 开始单调上升再下降”这种几何上的反常要求；要求的是**允许的竖直速度上限随 θ 单调减小**。

### 2.3 两条规则如何配合

- 规则 1 降低“选择陡目标”的频率；
- 规则 2 保证“即使选了陡目标，实际也走不快、走不直”；
- 若目标斜率超过 k，执行层会把它压回锥内；但目标可能因此永远到不了，所以再加**横向路点**（见 4.5）。
- 两者共用 k，调参时只需改一个数；如果想让陡方向更慢，可以再加一个只影响竖直分量的阻尼指数 m（可选，见 4.3）。

### 2.4 这不是普通的平行四边形

普通速度合成是：

```
v = vx·i + vy·j
```

两个分量独立，允许域是矩形/平行四边形。我们的规则是在这个基础上加一个**各向异性约束**：

- 斜率锥：允许域是“以原点为顶点、上下边界为 ±k、被最大速度圆弧截断”的扇形/楔形；
- 若用椭圆包络：允许域是 `(vx/s)² + (vy/(k·s))² ≤ 1` 的横向椭圆。

所以“平行四边形”升级成了“锥/椭圆”；直观上就是：横向是正常路面，纵向是“贵”的方向。

## 3. 先例：横版清关与 2.5D

### 3.1 Belt-scroll：x 横向、y 纵深

Brendan A R Sechter 的 2D 投影系列把 belt-scroll 拆得很清楚：`x` 是横向，`y` 是地面纵深，`z` 是离地高度；屏幕投影把纵深映射成屏幕 y 偏移，角色在“一条有限深度的地带”里前后走。影子固定在 `(x, y)` 地面点，跳跃只抬 sprite，不改变地面 y；绘制顺序按地面 y 排序。`[B]`

- 纯 belt-scroll **不缩放**精灵；精灵缩放是后来的变体（越近越大/越远越小）。`[B]`
- 格斗判定按“纵深车道”容差，而不是屏幕像素完全重合。`[B]`
- 常见实现把纵向速度打折；一个 Phaser/beat-em-up 示例用 `speed * 0.6` 作为上下速度，并把 y 夹在地板带内。`[B]`

**对我们的意义**：桌面就是一块“没有边界的横向地带”，屏幕 y 可以当地面纵深；纵向速度打折、限制在 work area 的上下带内，完全有先例。

### 3.2 侧视精灵怎么上下走

横版清关的常见“beat-em-up walk style”是：**只保留左右朝向的精灵，上下移动时复用左/右走路帧；记住最后的水平朝向，斜向时按水平输入决定朝向。** 不需要上下行走动画。`[B]`

这正好对应我们的 Spine 资产：只有 Move/Relax/Sit/Sleep/Interact，没有 up/down 行走；但我们可以：

- 纵向移动时继续播 Move；
- 朝向只由 `sign(vx)` 决定；
- 若 vx 太小，就不动（或选择横向路点），避免“原地垂直滑步”。

### 3.3 等距/2.5D 的速度

经典 2:1 等距投影下，纵向在屏幕上看起来只有横向的一半；很多等距游戏直接把纵向速度设为横向的 0.5，或者反过来补偿，让屏幕速度一致。`[C]`

这和我们的目标不同：

- 等距游戏是为了**让世界空间速度看起来一致**；
- 我们是为了**让侧视美术在纵向移动时不那么突兀**，主动把纵向变慢。

两者都使用“方向相关的速度”，但参数目的不同。

### 3.4 Desktop Goose 的旁证

- 原版 Desktop Goose 闭源；Linux 移植版 `goose.cpp` 用的是程序化 2.5D 骨架，`ISO_SCALE {1.3, 0.4}`；每段漫步目标有随机 `parabolicCurvature`，用切向力走出弧线；抢鼠标是独立的 `SNATCH_CURSOR` 状态。`[B]`
- 它不是“侧视精灵滑步”，而是“2.5D 投影＋程序化骨架”；所以它纵向移动自然，不能直接复制到我们的 Spine。
- 可借的是：**自由 2D 目标＋弧线漫步＋横向主导**；不可借的是它的等距骨架。

### 3.5 明日方舟的 2.5D 口径（需要留个注）

- PRTS 的作战机制资料能确认：敌人朝向只有左右两种，且按**游戏内摄像机 POV**判断，不是地图实际方向；短路径/倒退移动/碰撞箱与影子判定点偏移/失衡物理位移都可能造成“滑步”观感。`[B]`
- 一手资料**没有**直接把“近大远小”写成官方补偿机制；所以“2.5D 近大远小弥补滑步”可以作为我们的设计直觉，但不要当成明日方舟的官方解释。
- 对我们有用的结论是：**侧视左右朝向 + 2.5D 摄像机**是明日方舟本身就在用的语言；玩家对一定程度的滑步是有容忍度的。

## 4. 数学模型

### 4.1 目标分布：三角斜率

设本次漫步的最大斜率 `k`（例如 1/3）。采样：

```
u1, u2, u3 ~ Uniform(0,1)
slope = k * (u1 + u2 - 1)        // 三角分布，[-k, k]，峰值在 0
dx = sign * (dmin + (dmax - dmin) * u3)
dy = slope * dx
target = clamp((x + dx, y + dy), workArea)
```

性质：

- `|slope| ≤ k`，纯竖直概率为 0；
- 斜率密度在 0 处最高，向 ±k 线性降到 0；
- 例如 k=1/3：中位数 |slope|≈0.098（约 5.6°），约 25% 的目标 |slope|>1/6（约 9.5°），超过 0.8k 的只有 4%；
- 目标 x 距离仍可均匀/偏长，保证横向活动范围。

**替代方案：**

| 方法 | 形式 | 优点 | 缺点 |
|---|---|---|---|
| 三角斜率 | 密度在 `[-k,k]` 线性递减 | 简单、边界硬、易测 | 角度分布不完全等于 cos^n |
| `cos^n θ` 截断 | `p(θ) ∝ cos^nθ`，`θ∈[0,θmax]` | 角度语义直观、平滑 | 采样需拒绝/数值反演 |
| von Mises | `p(θ) ∝ exp(κ cosθ)` | 圆统计标准分布、参数少 | 采样较重，v1 没必要 |
| 截断正态 | `dy ~ N(0, σ²)`，截断 | 熟悉、可调 | 需要截断/重采样 |

v1 用三角斜率；如果实机觉得“太规则”，再换 cos^n 或给斜率加一点低频噪声。

### 4.2 执行：斜率锥

```
θ = atan2(|dy|, |dx|)
vx = s * cosθ * sign(dx)
vy = s * sinθ * sign(dy)
if |vy| > k * |vx|:
    vy = sign(vy) * k * |vx|
```

性质：

- `|vy| ≤ k|vx|` 恒成立（除非速度为 0）；
- 竖直速度上限 `k·s·cosθ` 随 θ 单调下降，θ=90° 时为 0；
- 目标在锥内时，实际方向不变；目标在锥外时被压平，或走横向路点；
- 最大速度仍为 s；斜率锥只限制方向，不额外降总速（除非目标本身速度低）。

**可选强化：** 如果实机仍觉得纵向太多，可以把竖直上限再乘 `cos^mθ`：

```
|vy| ≤ k * |vx| * cos^mθ     // m≥0；m=0 就是基础斜率锥
```

- m=0：基础锥，竖直上限 k·s·cosθ；
- m=1：竖直上限 k·s·cos²θ，陡方向更慢；
- 代价：实际路径更平，目标更可能到不了，需要路点/重选。
- 建议先 m=0，实机不够再升到 1；不要一开始就 m=2。

**椭圆包络（备选）：**

```
(vx / s)² + (vy / (k*s))² ≤ 1
```

给定目标速度，若在椭圆外，按射线与椭圆交点缩放。它的优点是平滑、横纵都有上限；缺点是纯竖直的最大速度是 k·s（常数），不像斜率锥那样随 θ 降到 0。可以把它当“安全上限”，斜率锥当“主规则”。

### 4.3 曲率：让路径不是直线

- 每段目标给一个小的 `curvature ∈ [-c, c]`（建议 c=0.2–0.3）。
- 在转向力里加切向分量，形成浅弧；靠近目标时曲率淡出，保证到达。
- 曲率产生的 vy 必须再次夹进斜率锥；否则弧线可能把路径带成竖直。
- 曲率是“生活感”来源，不是硬下限；v1 可以先关掉，等基础移动稳定再加。

### 4.4 到达与减速

- 距离小于 arrivalRadius（建议 10–16px）时视为到达；
- 减速时 vx、vy 同步缩小，斜率锥仍然成立；
- 不要在到达点“原地转身/原地上下”；
- 如果目标在 work area 边界被 clamp 后斜率超过 k，重新选目标或走路点。

### 4.5 太陡目标：横向路点

规则 2 会让“正上方/正下方”的目标永远到不了。处理：

```
if |dy| > k * |dx| or |dx| < dmin:
    // 先横向走到一个点，使剩余斜率落回锥内
    wx = x + sign(dx) * max(dmin, |dy| / k + margin)
    waypoint = (clamp(wx), y)
    // 先走 waypoint，再走 target
```

效果：

- 路径是“横走一段 + 浅斜线”，始终有水平分量；
- 不需要漂浮/跳跃/新动画；
- 会绕一点路，但这是“更多侧向移动”的代价；
- 对随机漫步，直接重采样更简单；对未来的 `moveTo(x,y)`，走路点。

### 4.6 动画同步

- 移动时始终播 Move；朝向 `sign(vx)`；
- 如果 `|vx|` 低于阈值（例如 5px/s），不进入自主移动，避免原地竖直滑步；
- 动画播放速度可与实际速度挂钩：`rate = clamp(speed / nominalWalkSpeed, 0.75, 1.15)`；由于斜率锥下总速仍为 s（除减速/夹取），大多数时候 rate≈1；
- 纵向滑步是接受的；不要为了消除它去新增 up/down 动画（超出本轮）。
- 若以后加 y 深度缩放，注意脚底锚点与缩放同步；缩放会改变视觉速度，需重新测。

## 5. 视觉：为什么这套能看

### 5.1 侧视精灵的“地面契约”

横版清关的精灵也只画左右；上下移动时复用同一套走路帧。它们也会滑步，但玩家接受，因为：

1. **纵向是低频动作**，不是持续上下；
2. **纵向速度慢**，脚部滑动不明显；
3. **有地面/影子/纵深排序**，视觉系统把 y 解释成“远近”；
4. **战斗和移动分离**，上下走通常不是高速动作。

我们的两条规则正好对应 1、2：三角分布降低陡目标频率，斜率锥降低竖直速度。

### 5.2 我们能补的深度线索（可选）

- **轻微 y 缩放**：`scale = 1 + d * (y - centerY)/(workHeight/2)`，d≈0.03；顶部略小、底部略大。不要超过 ±5%，否则角色尺寸会跳。
- **脚底阴影/光晕**：固定在脚底，不随 sprite 高度变化；我们的窗口没有现成影子，加之前先做视觉原型。
- **y 排序**：我们只有一只/两只宠物，没有场景遮挡，y 排序不是必需；未来有多宠/窗口平台才需要。
- **不要**：大幅缩放、频繁上下、快速垂直移动、纯竖直。

### 5.3 明日方舟的注脚

PRTS 能确认的是左右朝向与摄像机 POV；不能确认“近大远小”是官方用来补偿滑步的机制。所以这部分我们按“设计直觉”使用，不写成“官方做法”。

| 双宠分离半径 | — | 70–90px | 简单避让时用 |
| 纵向边距 | — | 40px | 不贴屏幕上下边 |

初始建议：`k=1/3`、三角分布、曲率 0、缩放 0；先看“纯横向偏置”是否已经自然，再逐步加曲率和深度缩放。

## 7. 边界、拖拽、多宠、多屏

- **活动边界**：work area（排除任务栏）或整块屏幕；建议先 work area，底部留 40px 边距；顶部也留 40px，避免贴边。
- **纯竖直**：禁止自主纯竖直；`|vx|` 低于阈值就重新选目标/走路点；拖拽不受限。
- **拖拽松手**：保留当前 y；下一次自主目标按斜率锥生成，不强行回地面。
- **多宠**：分离力也可能产生纯竖直推力；对分离力也做斜率锥夹取，或只保留横向分离，避免把对方顶上去。
- **多屏/DPI**：沿用第三轮结论——内部物理坐标、入口转逻辑、每宠先绑定当前显示器；跨屏另开策略。不要用 `window.screen` 当活动范围。
- **点击穿透**：命中框是窗口局部坐标；窗口平移不需要重推包围盒，只有内容包围盒变化才推。沿用现有 Rust 8ms 轮询。
- **性能**：只在取整位置变化时 `setPosition`；`set_hit_boxes` 做脏检查；两只小窗先测，不要先上覆盖层。

## 8. 实现架构与测试

### 8.1 纯逻辑核心

新增 `src/pet/movement.ts`（名称可调），不 import React/Tauri/DOM/settings：

```
type Vec2 = { x: number; y: number };
type Bounds = { left: number; top: number; right: number; bottom: number };
type MoveState = {
  pos: Vec2;
  target: Vec2 | null;
  waypoint: Vec2 | null;
  facing: 1 | -1;
  mode: "idle" | "walk" | "turn" | "arrive";
  timer: number;
  seed: number;
};
step(state, dt, bounds, options): MoveState;
```

- 固定步长 60Hz 累加器；RNG 注入（mulberry32 或现有工具里的 seeded RNG）。
- `k`、`dmin`、`dmax`、曲率、到达半径都放进 options；不要在状态机里写死。
- 适配层只负责把 `pos` 映射到 `setPosition`、把 `facing/mode` 映射到动画、把包围盒推给 Rust。

### 8.2 测试清单（`tools/test-movement.ts`）

**分布测试（10k 次采样）：**

- `|slope| ≤ k` 恒成立；
- 纯竖直样本数 = 0；
- 中位数 `|slope| < 0.35k`；
- `P(|slope| > 0.8k) < 5%`；
- 同一 seed 下样本序列可复现。

**运动学测试：**

- 每一帧 `|vy| ≤ k|vx| + ε`；
- `|vx| < ε` 时，不允许 `|vy| > ε`；
- 速度不超过标称值；
- 到达半径内减速收敛，无抖振；
- 大 dt、0 dt、NaN/Infinity 不产生爆炸。

**可达性/边界：**

- 目标在锥外 → 生成横向 waypoint，最终到达；
- 目标在 work area 外 → clamp 或重选；
- 负坐标/多屏矩形/work area 转换正确；
- 拖拽接管/释放后状态合法。

**动画/朝向：**

- 朝向只跟 vx；vx=0 时不移动；
- Move 播放与移动状态一致；
- 转身 0.15s 不抖动。

### 8.3 验收指标（真机）

- 主观：看起来“主要在侧着走”，不是电梯；连续观察 2–3 分钟不累。
- 客观：纯竖直帧数 0；`|vy|/|vx|` 的最大值 ≤k；目标斜率分布中位数 <0.35k；掉帧/CPU 与现状同量级。
- 多屏：100%/125%/150% 各跑一次；拖拽/点击穿透/双宠不回归。

## 9. 方案对比与推荐

| 方案 | 目标分布 | 执行约束 | 优点 | 代价/结论 |
|---|---|---|---|---|
| **A 斜率锥（推荐）** | 三角斜率 `[-k,k]` | vy 上限 ≤ k·vx | 简单、精确满足两条、易测 | 太陡目标需路点；v1 首选 |
| B 斜率锥＋cos² 强化 | 同上 | vy 上限 ≤ k·vx·cos²θ | 陡方向更慢、更偏横 | 可能到不了目标；实机不够再升 |
| C 椭圆包络 | 三角或 cos^n | `(vx/s)²+(vy/(k·s))²≤1` | 平滑、有硬上限 | 纯竖直不为 0；当安全上限用 |
| D 地面线兜底 | 只选同层 | y 仅拖拽 | 最自然、最简单 | 不满足全屏自主纵向 |
| E 新增上下动画 | 任意 | 自由 2D | 视觉最自然 | 超出本轮；资产/授权/工期 |

**推荐：A。** 先用 `k=1/3`、曲率 0、缩放 0，把“横向偏置”跑出来；如果实机仍觉得纵向多，再升 B 的 cos² 强化；C 作为安全上限；D 作为兜底；E 留到以后。

## 10. 需要你拍板的事

1. **最大斜率**：先 1:3（推荐）还是直接 1:2？
2. **目标分布**：三角斜率（推荐，简单）还是 cos^n（更平滑、参数更抽象）？
3. **纯竖直**：完全禁止（推荐），还是允许极小概率？
4. **曲率**：v1 先 0（纯直斜线）还是直接加浅弧（更有生活感）？
5. **深度缩放**：v1 不加（推荐）还是做 ±3% 对照？
6. **陡目标处理**：接受“先横走一段”的路点绕行吗？（推荐接受）

后置：目标是否偏向用户/总控台；拖拽松手是否回地面；是否加 y 阴影；是否迁移覆盖层。这些不影响本轮硬下限。
